# YakSSA中基于闭包的跨过程数据流分析框架

g g

本报告深入剖析了YakSSA，一个基于静态单赋值（SSA）中间表示（IR）的代码分析系统中执行跨过程数据流分析部分的设计思路。

我们首先为纯函数建立基础分析模型，详细阐述数据流如何通过参数和返回值跨越函数调用边界。

随后，我们将此模型扩展至处理复杂的头等函数闭包，引入YakSSA为表示捕获的词法环境（freeValue、binding）和状态修改（side-effect）而设计的创新性IR构造。

通过详尽的示例和对分析算法的逐步拆解，我们展示了YakSSA如何为包含复杂控制流和状态行为的程序提供一个统一且显式的框架，以追踪数据依赖。

文章的最后，我们将YakSSA的设计置于更广阔的编译器研究视野中，将其显式的、基于IR的方法与内存SSA（Memory SSA）和跨过程mod/ref分析等成熟技术进行比较。

# 基于SSA的跨过程分析原理

本节将为后续讨论奠定理论基础，阐明为何静态单赋值（SSA）是数据流分析的强大基石，并引出将此分析扩展至跨越函数调用时所面临的特有挑战。

### 1.1. 静态单赋值形式中的数据流图



静态单赋值（Static Single-Assignment, SSA）是一种中间表示（IR），其核心特征是每个变量在其生命周期内只被赋值一次 。这一特性是现代优化编译器的基石，包括LLVM、GCC等 。

SSA形式最主要的优势在于它将变量的“使用-定义链”（use-def chain）变得极为明确。对于任何一个变量的使用点，都只有一个唯一的定义点，这使得编译器无需执行复杂的“到达定值分析”（reaching definition analysis）即可确定其数据来源 。本质上，SSA形式的IR本身就构成了一张精确的数据流图。

例如，在YakSSA的IR指令 `t_2 = t_1 + 2` 中，数据流关系一目了然：变量`t_2`的定义直接依赖于变量`t_1`和常量`2`的使用。这种清晰的依赖关系是所有后续分析的基础。



### 1.2. 跨过程的挑战：跨函数边界的数据传播

尽管SSA极大地简化了过程内（intraprocedural）分析，但跨过程分析（Interprocedural Analysis, IPA）则要复杂得多。

IPA要求追踪跨越函数调用的数据流，这涉及到将调用点的实际参数（实参）映射到被调用函数的\`形式参数（形参），处理函数返回值，并对函数调用可能产生的副作用进行建模。

现代编译器如LLVM和GCC采用了先进的IPA框架。这些框架通常首先构建程序的调用图（call graph），然后通过分析图中的强连通分量（Strongly Connected Components, SCCs）来处理递归调用。然而，这些分析过程可能非常复杂，并面临可伸缩性的挑战。YakSSA的设计理念正是基于一个核心前提：将这些跨过程的数据流连接尽可能地在IR层面进行显式化表达，这也是本报告的核心主题。

### 1.3. YakSSA中间表示概览

# 基础模型：分析纯函数



本节将详细阐述最简单的情形：追踪数据流通过纯函数。这一模型是后续处理闭包和副作用等更复杂情况的基线。

### 2.1. 在YakSSA IR中表示纯函数与调用



纯函数定义比较简单：`function funcName(format-parameter) return (return-value)`。

一个纯函数的行为完全由其输入参数决定，且没有可观察的副作用。

YakSSA通过IR直接映射这种结构。例如，一个简单的纯函数`f`及其在`main`函数中的调用可以表示为：

```Plain Text
/*
f = (a) => {
    return a + 2
}
target = f(1) 
*/

function f(t1): 
    t2 = t1 + 2 
    return t2 
   
function main():
    t3 = 1 
    t4 = call f(t3)
   ...
```

在此表示中，一个至关重要的设计选择是**显式区分形参和实参**。在函数`f`的定义中，`t_1`是形参；而在`main`函数的调用点，`t_3`是实参。这种分离是实现精确跨过程分析的基石，因为它允许分析器在不同的函数作用域之间建立明确的联系。



### 2.2. 纯函数数据流追踪机制

基于上述IR，我们可以对`t_4`的来源进行一步步的回溯分析。这个过程的核心是维护一个概念上的**分析调用栈（analysis call stack）**。这个栈并非程序运行时的调用栈，而是静态分析过程中用于记录和传递上下文信息的关键数据结构。

对`t_4`的分析过程如下：

1. 分析起点为`t_4`。其定义指令为`t_4 = call f(t_3)`。
2. 识别出这是一个跨过程转换。分析器需要“进入”函数`f`的内部。
3. 为此，我们将当前调用信息`call f(t_3)`压入分析调用栈。这个栈帧保存了从调用者到被调用者的所有上下文信息，最关键的是实参和形参的映射关系。
4. 由于我们是从一个函数调用的返回值开始回溯，分析器直接跳转到函数`f`内部的`return`语句，即`return t2`。
5. 分析目标转为`t_2`。我们继续从`t_2`向上回溯，其定义为`t_2 = t_1 + 2`。
6. `t_2
`的依赖关系分解为对`t_1`和常量`2`的依赖。常量`2`是分析的终点。
7. `t_1`是一个形参。此时，我们查询分析调用栈顶的栈帧`call f(t_3)`。通过这个上下文，分析器将形参`t_1`精确地映射到其对应的实参`t_3`。
8. 分析器“返回”到`main`函数的作用域，继续回溯`t_3`的来源。`t_3`的定义为常量`1`。
9. 分析终止。我们最终确定`t_4`的值来源于表达式`1 + 2`的计算结果。

这个看似简单的过程揭示了一个深刻的原理：分析算法必须模拟程序在运行时的动态语义才能保证其正确性。

在SSA中，不同函数内的变量（如`t_1`和`t_3`)是完全独立的。分析调用栈是连接这些独立作用域的唯一桥梁，它存储了跨作用域转换的上下文，从而使数据流图在函数边界处得以连接。



### 2.3. 理论背景：与跨过程优化的关联



这种基础的数据流分析是许多强大的跨过程优化（Interprocedural Optimization, IPO）的基石。例如，LLVM中实现的跨过程稀疏条件常量传播（Interprocedural Sparse Conditional Constant Propagation, IPSCCP）正是执行了类似的分析。通过追踪函数参数在调用链中的传递，IPSCCP可以确定某些参数在特定调用路径下是否为常量，从而触发函数特化、常量折叠和死代码消除等一系列优化。

另一个相关的优化是参数提升（Argument Promotion）(4)。如果分析发现一个以指针形式传递的参数在函数内部只被读取（load）而从未被写入，编译器就可以将优化为直接传递指针所指向的值，而非指针本身。这同样依赖于对参数在被调用函数内部使用方式的精确理解。

# 框架扩展至闭包：词法环境的建模



本节将引入第一个主要的复杂性：闭包。我们将展示YakSSA如何对词法环境的捕获进行建模，并将其视为函数参数的一种自然扩展。

### 3.1. 闭包的分析挑战：带状态的函数

```JSON
f = () => {
    return a 
}
```

在编程语言中，**闭包**（Closure）是一个包含函数代码以及其环境的记录。这里的环境是一个映射，它将函数内部使用的、但在其外部作用域中定义的**自由变量**（free variables）与这些变量在闭包创建时的值或引用绑定起来。

闭包的存在打破了纯函数的简单模型。一个闭包函数的行为不仅取决于其显式参数，还依赖于这份隐式捕获的状态。这是一个“函数+作用域集合”的概念。

对于数据流分析而言，这意味着必须有一种方法来追踪这些通过词法作用域捕获的隐式输入。

在编译器实现中，处理闭包通常需要一个称为**闭包转换**（closure conversion）的过程。此过程会将一个嵌套函数（即闭包）转化为一个顶层函数，这个新函数会额外接受一个参数——一个指向“环境”结构体的指针，该结构体中存储了所有被捕获的自由变量的值 (10)。这个过程通常比较复杂，并且可能涉及堆内存分配。



### 3.2. 捕获环境的表示：`freeValue`与`binding`构造

```JSON
/*
a = 1;
f = func() { 
    return a
}; 
target = f()
*/ 
func f() freeValue[t3:(name-a)]: 
    return t3 

func main():
    t0 = 1 
    t2 = call f() [t0]
```

YakSSA没有采用一个独立的闭包转换处理器，而是选择将闭包的概念直接整合到其IR中。这是通过引入两个新的构造实现的：

- `freeValue`：在函数定义中，使用`freeValue[...]`子句来声明该函数捕获的自由变量，并为它们指定在函数内部使用的形参名。例如：`func f() freeValue[t3:(name-a)]`。这明确声明了函数`f`需要一个名为`a`的自由变量的值，并且在`f`的函数体内，这个值将通过形参`t_3`来访问。
- `binding`：在函数调用点，使用`[...]`子句（在YakSSA中称为`binding`）来提供`freeValue`对应的实际值。例如：`t2 = call f() [t0]`。这个`binding`子句显式地将调用点上下文中的活动变量`t_0`（它持有变量`a`当时的值）与函数`f`所期望的`freeValue`形参`t_3`连接起来。



### 3.3. 通过捕获变量的数据流分析



借助`freeValue`和`binding`，我们可以无缝地将闭包的数据流分析整合到现有框架中。我们使用一个“读取外部变量”的示例进行分析：

```JSON
/*
a = 1;
f = func() { 
    return a
}; 
target = f()
*/ 
func f() freeValue[t3:(name-a)]: 
    return t3 

func main():
    t0 = 1 
    t2 = call f() [t0]
```

对`t_2`（即`target`）的分析过程如下：

1. 分析起点为`t_2`，其定义为`call f() [t0]`。
2. 将调用信息`call f() [t0]`压入分析调用栈。
3. 跳转到函数`f`内部的`return t3`。
4. 回溯`t_3`的来源。`t_3`在函数`f`的定义中被标记为`freeValue`形参。
5. 查询分析调用栈。栈顶的`binding`子句`[t0]`提供了`freeValue`形参`t_3`到`bindingValue`实参`t_0`的映射。
6. 分析返回`main`函数，继续回溯`t_0`，其定义为常量`1`。
7. 分析终止，结论为`target`（`t_2`）的值为`1`。



### 3.4. 模型背景：与闭包转换的类比



YakSSA的`freeValue`/`binding`机制在功能上与闭包转换的结果是同构的。

- 函数签名中的`freeValue`列表，类似于定义闭包环境结构体（environment struct）的布局。
- 调用点的`binding`列表，类似于在调用前分配并填充该环境结构体。
- 在函数内部访问一个`freeValue`，类似于从环境指针中加载一个字段的值。

YakSSA设计的关键优势在于，通过将这些信息提升为IR的一部分，它避免了隐藏的、复杂的转换过程。从捕获变量（`t_0`）到其在闭包内部的使用（`t_3`）的数据流，现在是数据流图中的一条显式边，与普通参数的处理方式完全一致。

这种设计实现了一种**输入的统一化**。在源语言中语义不同的显式参数和自由变量，在YakSSA的IR层面被抽象为统一的“函数输入”概念。这极大地简化了分析算法，因为它不再需要为常规参数和捕获变量编写两套不同的处理逻辑；它只需要统一地查询分析调用栈以获取正确的参数映射即可。这种设计选择体现了一种将复杂性吸收到核心数据流分析框架中的优雅策略，即将“捕获一个变量”简化为“传递一个隐式参数”。

本节将应对最艰巨的挑战：对状态突变（mutation）进行建模。我们将展示YakSSA的`side-effect`指令如何将状态变更具体化，使其成为数据流图中的一等公民。



### 4.1. 阻抗失配：函数式IR中的可变状态



SSA的本质是函数式的：每个变量一旦定义，其值就是不可变的。然而，副作用（side effects）——即函数修改其自身作用域之外的状态（例如，修改一个全局变量或一个通过引用捕获的变量）——完全违背了这一原则。

传统的解决方案是运行一个独立的跨过程**修改/读取分析（mod/ref分析）** 。该分析会为每个函数调用计算出一个摘要，指明该调用*可能*会读取（`ref`）或写入（`mod`）哪些全局变量或内存位置。然而，`mod/ref`分析存在显著的局限性。其信息通常是保守的（例如，只能得出“可能修改”的结论），并且这些信息位于SSA数据流图之外。

优化器可能知道调用`foo()`会影响变量`g`，但它不知道`g`的新值是什么，也没有直接的数据流边可供追踪。这严重限制了诸如公共子表达式消除、冗余加载/存储消除等优化的能力。



### 4.2. `side-effect`指令：在数据流图中具体化状态变更



为了克服`mod/ref`分析的局限性，YakSSA引入了一个创新的`side-effect`指令，用于显式地表示状态突变。

```Plain Text
t5 = side-effect (a=t2) by t4
```

该指令的语义可以解读为：“变量`a`的一个新版本被创建，命名为`t_5`。它的值由函数调用`t_4`内部的`t_2`的值所定义。”

这种设计巧妙地维护了SSA属性。变量`a`的旧值（在示例中为`t_3`）并未被“修改”；相反，一个全新的版本`t_5`被定义了出来。这正是**内存SSA**（Memory SSA）的核心思想，即对内存状态本身进行版本化 (18)。

`side-effect`指令可以看作是对内存状态更新的一种高级、语言无关的表示。

在学术界的内存SSA框架中，通常会引入Memory SSA**中的`μ` (mu) 和 `χ` (chi) 函数**。YakSSA的`side-effect`指令在功能上等同于`χ`  函数，它显式地为被修改的状态创建一个新的SSA名称，并将其与触发修改的调用指令关联起来。这种设计避免了在编译器中实现一个独立的、复杂的内存SSA构建过程。



### 4.3. 函数输入与输出的完整模型

至此，我们可以构建出YakSSA关于函数调用的完整、对称的模型：

- **函数输入** = 显式参数 + `freeValue`参数（捕获的变量）
- **函数输出** = `return`返回值 + `side-effect`值（新的状态）

这个统一的视角将一个函数调用简化为一个纯粹的转换函数，它将一组输入的SSA值映射到一组输出的SSA值。这种处理方式将一个带有副作用的命令式操作，转换为了一个函数式的**状态传递风格**（state-passing style）(17)。函数

`f`不再是“原地修改”变量`a`，而是接受`a`的旧状态（`t_3`）作为输入，并产生`a`的新状态（`t_5`）作为输出。这在概念上等同于将`f()`重写为`new_a = f(old_a)`。这种对状态变更的具体化，使得原本难以分析的命令式代码能够适用于函数式风格的分析技术。



### 4.4. 追踪穿越状态修改闭包的数据流



我们使用用户提供的“写入”示例来演示完整的分析流程：

```Plain Text
/*
a = 1; 
f = func() { 
    a += 2 
}; 
f(); 
print(a)
*/
function f() [t1(a)] side-effect(a=t2):
    t2 = t1 + 2 

function main():
    t3 = 1 // a
    t4 = call f() [t3] 
    t5 = side-effect (a=t2) by t4 // a 
    t6 = call print ( t5 ) 
```

对`t_5`（即调用`f`后`a`的值）的分析过程如下：

1. 分析起点为`t_5`。其定义为`side-effect (a=t2) by t4`。
2. 这是一个跨过程转换。该指令明确告诉我们，`t_5`的新值来源于调用`t_4`内部的`t_2`。
3. 根据`t_4`，我们将调用信息`call f() [t3]`压入分析调用栈。
4. 分析器直接跳转到函数`f`内部`t_2`的定义处。
5. 回溯`t_2`，其定义为`t_2 = t_1 + 2`。
6. `t_1`是一个`freeValue`（在此场景下隐式地通过引用传递）。查询分析调用栈，将`t_1`映射到其`bindingValue`实参`t_3`。
7. 分析返回`main`函数，继续回溯`t_3`，其定义为常量`1`。
8. 分析终止，结论为`t_5`的值来源于`1 + 2`。

`mod/ref`分析 (13) 实现相对简单，但其提供的“可能修改”信息过于保守，且不属于数据流图的一部分，限制了优化效果。

YakSSA则在这两者之间取得了务实的平衡。它比`mod/ref`分析更精确、更显式；同时，相比于一个庞大、独立的内存SSA框架，它的模型更简单，与核心IR的集成度更高。这种设计表明，YakSSA的战略定位并非要成为一个通用的、能处理所有复杂指针别名场景的指针分析框架，而是一个优先考虑IR清晰度和分析集成度的务实选择，尤其适用于高级语言或脚本语言这类更侧重于命名变量而非复杂指针运算的场景。



### 5.2. 对堆与指针分析的启示



目前YakSSA的示例主要集中于具名变量（如`a`）。一个功能完备的语言还需要处理匿名的、在堆上分配的对象以及更复杂的指针别名问题。

要将YakSSA扩展到这些领域，可以从针对堆对象的跨过程SSA研究中汲取灵感。例如，一些研究工作通过引入特殊的`\phi`节点来处理别名指针，包括用于加载的`\phi_L`、存储的`\phi_S`以及用于参数传递的`\phi_V`和`\phi_C` (22)。

更前沿的研究，如MEMOIR (24)，则提出了针对整个数据集合（如数组、映射）的SSA形式，将数据的逻辑组织结构与底层内存表示解耦。这代表了使内存操作适应SSA分析的最新技术水平，也为YakSSA这类系统指明了潜在的未来发展方向。

### 5.3. 利用精确数据流信息赋能高级优化

拥有了对值和状态的精确、显式的数据流信息后，YakSSA能够支持一系列强大的优化，这些优化在使用不那么精确的分析时是难以实现的。

例如，可以更激进地进行**冗余加载消除**和**循环不变量代码外提**（特别是针对从闭包捕获的变量的加载/存储操作）(16)。考虑一个场景：一个闭包在循环中被多次调用，但其捕获的环境在此期间并未发生变化。那么，闭包内部那些仅依赖于捕获环境的计算就可以被安全地提升到循环外部，或者进行公共子表达式消除。这些优化都依赖于YakSSA提供的精确的、贯穿函数边界的数据流图。



# 结论



本报告系统地阐述了YakSSA的设计哲学与技术实现。YakSSA通过对称地处理函数的输入（显式参数与捕获变量）和输出（返回值与副作用），提供了一个统一且显式的、基于IR的跨过程数据流分析框架。

YakSSA的核心设计理念在于，将诸如词法捕获和状态突变这类复杂的源语言语义，直接**具体化**（reify）为数据流图中的一等公民。通过`freeValue`/`binding`和`side-effect`等IR构造，YakSSA将隐式的上下文依赖和状态变更转换为了图中清晰可见的数据流边。这种设计选择，以牺牲对最复杂指针别名场景的通用性为代价，换取了一个更简单、集成度更高、语义更清晰的分析模型。对于那些以具名变量和词法作用域为核心的高级语言而言，YakSSA的这种务实权衡，无疑是一种优雅且强大的设计。
